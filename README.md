# NailScan Try

The live demo scanner at **try.nailscan.ai**. A salon owner photographs her own
nails, gets the real NailScan report, and becomes a captured lead.

It is the proof stage of the funnel: `go.nailscan.ai/watch` sells, `/try` proves,
Maya calls in five minutes.

This repo exists because the previous white-label build was lost — the Pages
project was direct-upload with no source control. **Every deploy comes from here.**

## Layout

```
public/            Pages deploy root. SITE FILES ONLY — anything in here becomes
  index.html       a public URL. Put tooling, notes and configs in a sibling dir.
  config.js        White-label boundary. Brand, theme, gate thresholds, copy.
  css/app.css      One stylesheet, no framework.
  js/gate.js       Client-side lighting gate. Standalone, no dependencies.
  js/app.js        Flow controller.
  _headers         Security headers + cache policy.

api/               Cloudflare Worker `nailscan-try-api`. NOT in the deploy root.
  src/index.js     Cloned from based-nail-scanner; engine unchanged.
  wrangler.toml

docs/
  api-contract.md  The extracted contract of the existing scanner (Step 0).
  deploy.md        Deploy, DNS, GHL, and what is currently blocked.

test/
  gate-harness.html   Runs the gate against fixtures in a browser.
  fixtures/           Real nail photo + darkened / backlit / blurred variants.
  mock-api.py         Local dev server: serves public/ and mocks both endpoints.
  mkrecord.mjs        Regenerates the mock record using the REAL worker engine.
```

## Run it locally

```bash
python3 test/mock-api.py
```

Serves `public/` on <http://127.0.0.1:8791> with `/api/analyze-nails` and
`/api/lead` mocked. The mocked record is generated by the actual Worker engine
(`test/mkrecord.mjs` → `buildRecord`), so the front-end always renders the true
schema rather than a hand-written stub. `MOCK_DELAY=14 python3 test/mock-api.py`
stretches the fake vision call out if you want to look at the analyzing stage.

Camera capture needs a secure context — `localhost` counts, so `getUserMedia`
works over plain HTTP here.

## The lighting gate

The known flaw in the old scanner: it accepted bad-lighting shots and produced
weak reads. The server had a quality check, but it fired *after* a paid vision
call and reported the miss as a "couldn't read" tier instead of asking for a
retake.

`public/js/gate.js` runs on the captured frame **before upload**. A rejected
photo never leaves the device. Three measurements on one downscaled pass:

| metric | what it catches | v1 behaviour |
|---|---|---|
| `meanLuma` | flat underexposure | reject below 60/255 |
| `shadowPct` | hands in shadow against a bright window — mean passes, nails don't | reject above 40% |
| `laplacianVar` | soft focus | **warn only** |

Thresholds live in `config.js`, not in code, because they need tuning against
real photos.

Verify with `test/gate-harness.html` (served by the mock server at
`/../test/gate-harness.html`, or any static server from the repo root). Current
fixture run — all five match expectation:

| fixture | expect | got | meanLuma | shadow% | lapVar |
|---|---|---|---|---|---|
| `01-window-lit` real photo | PASS | PASS | 166.6 | 0.9 | 735.4 |
| `02-dim-room` ×0.22 | REJECT | REJECT `too_dark` | 35.8 | 20.1 | 17.8 |
| `03-dark` ×0.10 | REJECT | REJECT `too_dark,shadowed` | 16.0 | 100.0 | 3.5 |
| `04-backlit` | REJECT | REJECT `shadowed` | **89.8** | **41.1** | 112.0 |
| `05-soft-focus` blur 4.5 | PASS + warn | PASS `soft_focus` | 166.7 | 0.0 | 4.0 |

The backlit row is the case that justifies two metrics: mean brightness of 89.8
sails past the threshold, and only the shadow fraction catches it.

Known tuning item: `laplacianVar` is not normalised for exposure, so dark photos
also read as soft. It is warn-only, and those photos are rejected on brightness
anyway — but normalise it before it is ever allowed to reject.

## White-labelling

`public/config.js` is the only file that changes between deployments. It carries
the brand, the theme (written straight onto `:root` as custom properties, so a
new palette needs no CSS edit), the gate thresholds, the consent line and the
cross-link. The Worker has a matching `BRAND` object at the top of
`api/src/index.js`.

**There are no client-facing branding controls anywhere, by design.** The sold
product reuses this same app with a per-salon config generated on our side.

## Copy rules

Deadpan, forensic, specific. No exclamation marks. Banned: *pamper, indulge,
luxurious, amazing, excited*. Numbers stated flat.

No medical or diagnostic claims — the assessment is cosmetic, and the Worker's
`medical` tier says so explicitly rather than naming anything. The consent line
is reproduced verbatim from the brief and must stay that way. Pricing and
all-sales-final live on `/watch`, never here.

## The plan

`public/js/plan.js` + `public/js/calendar.js` turn the reading into dates
somebody will actually keep.

The reading's own milestones come through untouched — the Worker computed them
and nothing on the client edits them. What the planner adds is the two things a
photo cannot know:

* **what she had done today**, which sets the rebook rhythm (gel three weeks,
  BIAB four, a gel pedicure six — the numbers live in `config.js`, not in code)
* **what she has coming up**, which it works backwards from: two to five days
  before the day itself, past the setting window and short of any grow-out

It also says when those two disagree. A removal due on or before the wedding is
called out, because that is the case where following the pretty calendar and
following the reading are not the same thing.

Export is a plain `.ics` download plus Google's own prefill link — no sign-in, no
OAuth client, nothing of hers held by us, and it works on the phone she is
holding. All-day events with a reminder the day before, folded at 75 octets,
because a calendar file that one phone rejects is worse than no file.

The whole thing is pure functions with no DOM and no network, so
`test/plan-test.mjs` can check the arithmetic — 42 assertions covering the
intervals, the event maths, the clash detection and the file format:

```
node test/plan-test.mjs
```

The saved-reading page mounts the same planner, so the link in her email is not
a flat copy of what she saw: she can come back in three weeks, tell it about a
wedding, and get new dates out of the same reading.
